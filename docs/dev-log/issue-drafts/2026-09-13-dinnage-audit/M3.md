TITLE: [Dinnage audit M3] fixed_gradient's absolute tolerance warns on almost every correct fit at n>=1000
LABELS: audit-dinnage, bug, major
---
Reported by Russell Dinnage, independent evaluation of drmTMB 0.7.0 at 945da24f
(https://github.com/rdinnager/drmTMB_eval/blob/main/REPORT.md §4, Appendix A row M3; severity major).
Supporting working: none cited beyond the reproduction in §4

## What Russell found
`check_drm()`'s `fixed_gradient` row uses a fixed absolute threshold (`gradient_tolerance = 1e-3`) on
a gradient that is a sum over `n`, so it scales with sample size while the threshold does not. On
correctly-specified, `glmmTMB`-cross-checked fits, the false-positive rate rose from 3/20 at n=100 to
20/20 at n=4000; four other, independently run campaigns reproduced the same pattern (62% to 99.3% on
a skew-normal design; 28% to 99% on a second Gaussian design; 56.6% on a correct 300-row weighted
fit). The relative gradient (`max|g| / |logLik|`) stays flat at ~3e-6 across sample sizes — these fits
are converged by any normal standard. Because `attr(check_drm(fit), "ok")` rolls this row into the
one flag a busy user reads, an all-green board stops being evidence of health at realistic `n`. This
is also why C1 is worse than it looks: the wrong and healthy fits in C1's reproduction get identical
status labels because the guard that should distinguish them fires on both.

## Where (at 945da24f)
`R/check.R:612` (`gradient_tolerance` default and `check_fixed_gradient`'s absolute comparison).

## Since-audit status on main (4bfb9d721, 2026-09-13)
PRESENT. `gradient_tolerance = 1e-3` is still the default at `R/check.R:264`, and
`check_fixed_gradient()` (now at `R/check.R:623`, drifted ~11 lines from the report's :612) still
compares absolutely: `ok <- max_abs <= gradient_tolerance` at `R/check.R:662`. No sqrt(n) or
relative-gradient scaling is present anywhere in the function. No existing-issue match found;
`gh issue list --search "fixed_gradient"` and "gradient_tolerance" return nothing on point (issue
#1251, on `hessian_conditioning`, is a different check with a different miscalibration and is not a
duplicate).

## Proposed fix (Russell's, if stated)
Scale the tolerance by sqrt(n) (report measured 11.8x growth for a 100x change in n, i.e. sqrt(n) not
n), which restored `ok` on 97-100% of correct fits in the report's re-test; a fixed absolute
tolerance was refuted directly (loosening to 1e-2 still fired on 32% of correct n=10,000 fits while
a genuinely unbounded likelihood was still caught 100/100). `gradient_tolerance` is already a
documented, user-settable argument, so the fix is rescaling the default, not adding a knob.
