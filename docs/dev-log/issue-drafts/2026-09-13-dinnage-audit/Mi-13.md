LABELS: audit-dinnage, bug, minor

Reported by Russell Dinnage, independent evaluation of drmTMB 0.7.0 at 945da24f
(https://github.com/rdinnager/drmTMB_eval/blob/main/REPORT.md §4, Appendix A row Mi-13; severity minor).
Supporting working: `DESCRIPTION` vs `git tag` at the audit pin.

## What Russell found
At 945da24f, `DESCRIPTION` said `Version: 0.7.0` while the newest remote tag was `v0.5.0` -- two releases
of NEWS with no immutable pointer, in a repo with ~2,633 commits and 869 branches. "One command" fix (tag
the release).

## Where (at 945da24f)
`DESCRIPTION`, git tags.

## Since-audit status on main (4bfb9d721, 2026-09-13)
MOVED. The specific two-release gap Russell measured is closed: `git tag --sort=-creatordate` now shows
`v0.7.0` (plus `v0.5.0`, `v0.4.0`), so `DESCRIPTION`'s 0.7.0 state is now tagged. But the underlying
pattern has recurred one step later: `DESCRIPTION:3` now reads `Version: 0.7.1`, and there is no `v0.7.1`
tag -- `DESCRIPTION` is again one version ahead of the newest immutable tag. `git log --oneline
945da24f..HEAD -- DESCRIPTION` shows the version bumps that produced this drift. No existing-issue match:
`gh issue list --search "DESCRIPTION version"` and `--search "git tag"` return nothing on point; #61
("Phase 20: CRAN readiness and paper-preparation gate") is a much broader release-readiness umbrella, not
this specific tagging-cadence gap.

## Proposed fix (Russell's, if stated)
"One command" -- tag the release matching the current `DESCRIPTION` version (`v0.7.1`), and consider a CI
check that fails when `DESCRIPTION`'s Version has no matching tag on `main`.
