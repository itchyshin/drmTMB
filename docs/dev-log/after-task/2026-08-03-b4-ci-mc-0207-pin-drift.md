# After Task: B4-CI C1-C4 pin drift against the Arc 4b mc-0207 split

## Goal

Not a new feature. This is a finding, surfaced while merging Arc 5 (#907)
and Arc 6 (#908) onto current `main`: an attempt to wire the five
orphaned `tools/tests/test_*.py` files into CI (alongside the twelve
model-surface promotions those PRs land) uncovered that four of the five
already fail, independent of either PR.

## What Was Found

`tools/integrate_b4_ci_c1.py` through `tools/integrate_b4_ci_c4.py` each
fail their `--check` / `--check-current` mode on unmodified
`origin/main` (`ca46559f3fe020c8e1e363b02d7a9306b65d2c33`), verified in a
clean, detached `git worktree add --detach <tmp> origin/main`, with
nothing from Arc 5/6 present:

```
$ python3 tools/integrate_b4_ci_c1.py --check-current
B4-CI C1: a hard-excluded C1 neighbour changed from the frozen base

$ python3 tools/integrate_b4_ci_c2.py --check
B4-CI C2: C1, B3, or excluded base-row drift

$ python3 tools/integrate_b4_ci_c3.py --check-with-later-cohorts
B4-CI C3: C3 cell source or claim-boundary drift

$ python3 tools/integrate_b4_ci_c4.py --check
B4-CI C4: protected base-row drift
```

## Root Cause

All four scripts define the same `EXCLUDED_IDS = {"mc-0182", "mc-0183",
"mc-0207", "mc-0269"}` -- cells considered but deliberately excluded from
their respective promotion cohorts -- and all four assert those rows
have not changed since the cohort was integrated. PR #905 (Arc 4b,
`a55ddaef8`) split `mc-0207` into three per-q leaves
(`mc-0207`/`mc-0715`/`mc-0716`) and demoted it from `point_fit_recovery`
to `evidence_tier=none`, with its own review (Noether/Fisher/Rose) and
its own capability-ledger invariants (`FROZEN_CENSUS_POINT_FIT_RECOVERY`)
satisfied. But nothing wired these four B4-CI scripts into CI at any
point (see `docs/dev-log/after-task/2026-08-01-b4-ci-c1-rebase-canonical-
integration.md` through `2026-08-02-b4-ci-c4-canonical-integration.md`:
each was run once, by hand, at its own integration time, and never added
to `.github/workflows/R-CMD-check.yaml`), so nobody -- human or CI --
checked whether the Arc 4b split was compatible with what these four
guards protect. It was not.

The four scripts are not uniform in mechanism, which matters for any
future fix:

- **C1** (`integrate_b4_ci_c1.py:296`) compares a SHA256 of the current
  excluded rows against a static literal, `EXCLUDED_BASE_ROWS_SHA256`.
  This is mechanically recomputable: patching just that one constant (in
  memory only, nothing written) makes `check_current()` pass fully, with
  no other failure behind it.
- **C2/C3/C4** (`integrate_b4_ci_c{2,3,4}.py`, each via a `base_cells()`
  helper) instead compare the current local rows directly against
  `git show <BASE_COMMIT>:.../cells.tsv` -- a specific historical commit,
  not a literal. There is no hash to recompute; the only ways to make
  these pass are to advance `BASE_COMMIT` to a point after the Arc 4b
  split, or to drop `mc-0207` from `EXCLUDED_IDS`, and both changes
  redefine what "protected" has meant for these closures since they were
  written.

## Why This Was Not Fixed Here

Deciding whether the Arc 4b split is an approved base change for the
B4-CI C1-C4 closures is an owner decision, not a mechanical one -- it
requires knowing why these four cells were excluded from their cohorts
in the first place, and whether that reasoning still holds now that
`mc-0207` itself has been restructured. That context does not belong to
the Arc 5/6 census-count merge this finding surfaced during. Fixing it
by recomputing hashes or advancing `BASE_COMMIT` without that context
would risk exactly the kind of laundering these guards exist to
prevent.

## Disposition

- `test_b3_q6_target_promotion.py` (the fifth orphaned file, and the one
  directly exercised by Arc 5/6's promotions) is fixed and wired into
  `.github/workflows/R-CMD-check.yaml` as an explicit per-file
  invocation, alongside the two guards already there. CI goes from 2 of
  7 `tools/tests/` files run to 3 of 7.
- `test_b4_ci_c1.py` through `test_b4_ci_c4.py` remain un-wired and are
  not skipped/xfailed either -- the workflow carries a comment naming
  them and this note, so the gap stays visible rather than silent.
  `unittest discover` was deliberately not adopted as the replacement
  mechanism for this reason: it would silently re-include all four the
  moment someone made that swap for an unrelated reason.

## Next Actions

An owner (or a dedicated follow-up task) needs to decide, per script,
whether `BASE_COMMIT` should advance past `a55ddaef8`/`e8780dbe5`, or
whether `mc-0207` should leave `EXCLUDED_IDS` given it no longer denotes
a single cell. Only after that decision should C1-C4 be wired into CI.
