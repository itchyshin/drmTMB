# p-1144: the parity half of #1144 -- ordered cutpoints through `engine = "julia"` are discoverable, and refused by name

**Reader**: anyone reading `profile_targets()` or calling `confint()` on an
`engine = "julia"` `cumulative_logit()` fit; anyone widening DRM.jl's bridge
inference targets beyond `fixef:` and `sd:`; anyone auditing which #1144
obligations are met on which engine. Leaf ledger:
`.unlazy/parity/gates/leaf-p-1144-cutpoints.md`. Worktree branch
`claude/parity-p-1144-cutpoints` from `origin/main` at `4c1f5a63a`. DRM.jl pin
`430ef64cc`.

## 1. Goal

drmTMB issue #1144 is CLOSED and its **native** ask is already on `main`
(PR #1178, verified below, not re-done here): both constrained
`stats::nlminb()` sites in `R/profile.R` are Newton-polished under
`object$control$newton_polish`, and a native `cumulative_logit()` cutpoint
profile interval returns finite bounds with `conf.status == "profile"`.

`cumulative_logit` is an **admitted bridge family**
(`R/julia-family-registry.R`, A4 2026-09-05). The parity obligation is
therefore the other half of the same question: what #1144 made true natively
must also be true through `engine = "julia"`, **or be explicitly and testably
refused there**. This leaf measured that half first, then closed the gap it
found.

## 2. Implemented

* `R/julia-family-cumulative_logit.R` (new block, ~150 lines):
  * `drm_julia_cumulative_logit_targets(object)` -- the ordinal inventory for
    a Julia-engine fit, mirroring the native `drm_profile_targets()` block
    row for row: two `ordinal:theta_ord:<label>` internal rows
    (`profile_ready = FALSE`, note `internal_ordinal_parameter`, as natively)
    and two public `ordinal:cutpoint:<label>` rows (`profile_ready = FALSE`,
    new note `julia_ordinal_cutpoint_native_only`). Returns
    `empty_profile_targets()` for any fit with no `ordinal` slot, so the
    union call site needs no family guard.
  * `drm_julia_is_ordinal_parm(object, parm)` -- TRUE only when `parm` names a
    row of **this fit's own** inventory, so a mistyped label keeps the
    ordinary unknown-target message.
  * `drm_julia_ordinal_interval_refusal(object, parm, method)` -- the refusal.
* `R/julia-bridge.R`: one guarded call at the top of `confint.drmTMB_julia()`,
  placed **before** the method branch so `"wald"`, `"profile"` and
  `"bootstrap"` all answer identically; plus the roxygen paragraph stating the
  engine boundary.
* `R/profile.R`: two hunks only -- one `rbind` line adding the ordinal rows to
  `drm_julia_profile_target_union()`, and `julia_ordinal_cutpoint_native_only`
  added to `validate_profile_targets()`'s `allowed_notes`.
* `man/confint.drmTMB_julia.Rd` regenerated (roxygen only; byte-identical to a
  fresh `roxygenise()` run, and no other `man/` file changed).
* `NEWS.md`: one section.
* `tests/testthat/test-julia-family-cumulative_logit.R`: seven new blocks plus
  the parity evidence folded into the existing live round trip.

**No numbers changed on either engine.** This is discovery + diagnosis + an
explicit engine boundary.

## 3a. Decisions and Rejected Alternatives

* **Rejected: route the cutpoint interval through the bridge.** Measured at the
  pin: `_bridge_parse_inference_parm` (`src/bridge.jl`) accepts only
  `fixef:<dpar>:<coef>` and `sd:<...>`. There is no cutpoint inference target
  at `430ef64cc`, so a cutpoint interval cannot be routed without a DRM.jl
  change. Refusal is the honest outcome, not a shortcut; inventing a Wald
  interval from the cutpoint's delta-method SE would have been worse, because
  the **native** engine deliberately refuses Wald for ordered cutpoints too.
* **Rejected: leave the rows out of discovery and only fix the message.** Then
  `profile_targets()` would still under-report what is on the fit, and the
  user could not find the cutpoint name to ask about. Design 168 wants a
  capability that is discoverable and honestly labelled, so the rows are
  listed with `profile_ready = FALSE` and a note -- the same treatment the
  `sigma` response-scale alias row already gets.
* **Chosen: refuse before the method branch, not inside each one.** One guard,
  one message, three methods.

## 6. Tests of the Tests

* **File-level red control (G7)**: the one guard in `confint.drmTMB_julia()`
  was neutralised to `if (FALSE)`. The three refusal blocks then went red with
  the exact pre-fix defect --
  `Error in profile_match_confint_targets(...): Unknown confidence-interval
  target: "ordinal:cutpoint:low|medium".` -- and `R/julia-bridge.R` was
  restored byte-identically (sha256 `34ac09f5...4624` before and after).
* **In-suite red control**: a `local_mocked_bindings()` block pins the same
  thing permanently, so a later edit that drops the predicate fails CI.
* **The gate counter was itself wrong, and the red control caught it.** The
  first red run reported `fail=0` and looked green. The three refusal blocks
  had produced testthat **errors**, not failures, and `sum(r$failed)` does not
  see `r$error`. G6 and G9 now count `sum(r$error)` as well; without that, an
  errored suite would have scored as a pass.

## 8. Consistency Audit

* The Julia ordinal rows use the **same** column vocabulary as the native rows
  (`scale = "cutpoint"`, `transformation = "ordered_cutpoint"`,
  `target_type = "constrained"`, `tmb_parameter = "theta_ord"`), so
  `profile_targets()` output is comparable across engines without special
  cases.
* Both engines now refuse a **Wald** cutpoint interval; only the profile route
  stays native-only. The two messages differ deliberately: the native one
  names `method = "profile"`, the Julia one names `engine = "tmb"`.
* `drm_julia_confint()` / `drm_julia_bootstrap_confint()` build their own
  target `rbind()` and were deliberately left untouched -- widening those
  would duplicate fixed-effect rows and break the one-target validator (the
  reason the union exists separately, per the comment already in
  `R/profile.R`).

## 9. What Did Not Go Smoothly

* **The dispatch brief said this worktree had done no work.** It had: a full
  ledger and a complete implementation were sitting uncommitted. Reading the
  tree rather than the brief saved a rewrite.
* **A latent cli defect, found by re-reading rather than by a test.** The
  refusal pasted the collapsed label text **into** the cli format string, and
  cli glue-expands that string. Measured: an `a{1}|b` cutpoint came back as
  `Requested: "ordinal:cutpoint:a1|b"` -- the refusal quoted, and told the
  user to use, a target name that does not exist on the fit. Ordered factor
  levels may legally contain braces, so this is reachable. Fixed by
  interpolating single pre-collapsed **variables** (`"{requested_line}"`),
  which cli inserts literally; pinned by a new test.
* **`sum(r$failed)` is not a pass criterion** -- see section 6.

## 10. Known Residuals

* **A mixed `parm` vector is refused whole.** `confint(fj, parm =
  c("fixef:mu:x", "ordinal:cutpoint:low|medium"), method = "profile")` refuses
  the entire call rather than returning the fixed-effect row and refusing the
  cutpoint. Refusing is safe and honest; splitting the request was out of
  scope and is not tested here.
* **No cutpoint interval exists on the Julia engine at all.** Closing that
  needs a cutpoint inference target in DRM.jl's `_bridge_parse_inference_parm`
  plus a constrained cutpoint solve on the Julia side. Not attempted.
* **No coverage claim.** Nothing here is interval-coverage evidence on either
  engine; the native cutpoint interval's calibration is unchanged and
  unmeasured by this leaf.
* **One fixture, one seed** (n = 900, seed 20260509, fixed-effect only). The
  random-intercept cutpoint fixture used by PR #1178's native test was not
  re-fitted through the bridge -- `cumulative_logit` is admitted on the
  fixed-effect route only, so a random-intercept bridge fit is refused before
  Julia starts.

## 11. Team Learning

A negative gate is only worth what its counter can see. `sum(r$failed) == 0`
looked like a green red-control and was in fact three errored blocks. Any
testthat gate in this programme should count `error` alongside `failed`, and
`skipped` alongside both.
