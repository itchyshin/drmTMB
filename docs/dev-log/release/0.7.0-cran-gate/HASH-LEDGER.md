# drmTMB 0.7.0 — hash ledger

**Written by:** Grace (reproducibility/CI engineer) · **Date:** 2026-08-09
**Purpose:** reconcile every 0.7.0-era artifact SHA-256 found in circulation across
`origin/main`, `origin/claude/07-release-slice`, and `origin/claude/boundary-surfacing`, and
record — per CRAN release gate Gate 6 — which hash each CI/win-builder/R-hub run actually tested.
**Method:** `git show <ref>:<path>` on all three refs, `grep -rhoE '[a-f0-9]{64}'` over
`docs/dev-log/release/0.7.0-cran-gate/`, `docs/dev-log/release-audits/`, and
`docs/dev-log/check-log.md`; `shasum -a 256` recomputed directly on the preserved candidate-A
bytes; `gh run list` / `gh run view` cross-referenced against exact commit SHAs; `git diff
--name-only` / `git merge-base --is-ancestor` used to test path-identity and ancestry claims made
in-repo before repeating them here.

**No rung claim is made or implied by this document.** It is a provenance map, not a gate result.

## What this means for platform-clean

No platform evidence — GitHub Actions, win-builder, or R-hub — was ever run against the literal
bytes of the current candidate tarball (`a8f7c47905b0…`, source `cc4f5baee`), because GitHub
Actions always rebuilds from a checkout rather than testing an uploaded tarball. The closest
attachment is two `workflow_dispatch` runs (`R-CMD-check` 31336312020, `R-hub` 31336313176) at
commit `604016a5d`, which is two docs-only commits ahead of `cc4f5baee`; I independently re-ran
`git diff --name-only cc4f5baee 604016a5d` and confirmed the only changed paths are `AGENTS.md`
and files under `docs/`, both `.Rbuildignore`d, so the *content* those runs built is
byte-for-byte equivalent to the candidate. No win-builder submission exists for this candidate at
all — every win-builder run in this directory belongs to 0.6.0 predecessor artifacts (`c787ee40…`,
`f9b9588e…`). So: 3-OS GHA and R-hub coverage exists for the current candidate's *content* (not its
literal tarball hash); win-builder, valgrind, and rchk coverage do not exist for it at any level —
those results all belong to superseded 0.6.0 or superseded 0.7.0-candidate artifacts and, per Gate
6, cannot be reused. A genuine `platform-clean` claim would need at minimum a fresh win-builder
(R-release + R-devel) submission of the current candidate tarball; the GHA/R-hub runs at `604016a5d`
can likely stand once that content-identity argument is accepted by the owner, but they were not
literally dispatched at `cc4f5baee`, `d04d0e88`, or the current tip `bce9cfb6f`.

  they are "source commits, not hashes" does not hold; I verified this directly rather than
  reproducing the premise.
