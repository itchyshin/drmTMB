## 4. The `n_attempt` verification result

**Independently verified against the code; the specific mechanism I hypothesised was wrong, and
Noether's direct check against the artifact supplies the correct one. Recording both for the
record.**

**What the code shows (unchanged from my own read):**
1. `mr_g5_summarise_attempts()` (`inst/sim/R/sim_missing_response_g4g5.R:905-935`) sets
   `n_attempt = nrow(x)` — a **measured** row count — and line 921-923 hard-stops
   (`stop("Each G5 cell must retain exactly its planned number of attempts.")`) if
   `nrow(x) != planned` for any cell in the group being summarised. I traced this guard through
   `git log -p -L 900,935` across all three prior revisions of the function (`908c9923`,
   `d85ffe22`, `d59a0a3a`) — the exact-count guard has existed since the function was first
   written and was never relaxed.
2. `mr_g5_reconcile_checkpoints()` does field-*padding* (union of column names, NA-fill for
   missing fields, line 1324-1328) so failure records with fewer columns `rbind()` cleanly. This is
   column padding, not row padding — it never fabricates additional attempt rows to reach 1200. The
   comment at line 1400-1401 ("pad, matching what `mr_g5_reconcile_checkpoints()` already does
   downstream") refers to this field-union behaviour, not replicate-count fabrication.
3. Arithmetic check on the artifact cited as evidence: 348,000 records ÷ 1200 = exactly 290 —
   matching the CSV's row count exactly. This is consistent with the truncated `beta` `2x` cells
   being absent from the evidence artifact rather than present with a padded denominator.

**My working hypothesis was incomplete.** I read (1)-(3) as meaning the *whole reconcile call*
would abort if a truncated cell were included — true — and inferred from that alone that the
truncated cells must simply never have been fed to the guarded function. That is correct as far as
it goes, but I did not identify the actual point in the pipeline where the exclusion happens.

**Corrected mechanism (Noether, verified independently against `rorqual:~/g5run/g5-reconciled-final.rds$summary`):**
`n_attempt == nrow(x)` holds for all 290 cells — confirmed directly against the artifact, not
inferred. The truncated `beta` `2x` cells are absent from `$summary` because **incomplete cells are
dropped from the embedded registry before the completeness check runs**, not because the
completeness check ever evaluates and rejects them. Concretely: `mr-g5-reconcile-cohort.R` (and
the analogous full reconcile driver) selects a `route_ids` / cell subset via
`mr_g5_select_routes()`/registry filtering (`tools/mr-g5-reconcile-cohort.R:24`,
`tools/mr-g5-reconcile.R:31-33`) *before* `mr_g5_summarise_attempts()` and
`mr_g5_calibration_gate()` ever run. If the truncated cells were never included in the route subset
handed to the reconciler for the final `authenticated_uncentred` run, `calibration_complete`
(`out$calibration_complete <- out$n_attempt == out$n_planned`, line 960) is checking a population
that by construction excludes every incomplete cell — **the completeness check passes vacuously**,
because it is never asked to evaluate the cells that would fail it. This is not the same defect
family as "n_attempt reports registry intent" (which the code disproves — n_attempt is always
measured); it is a **selection-before-verification gap**: the gate that is supposed to catch
incompleteness never sees an incomplete cell, so a silently-shrunk admission set and a fully-
verified admission set produce an identical-looking `calibration_status = "pass"` output. The
`stop()` guard in `mr_g5_summarise_attempts()` is a correctness backstop for cells that *do* reach
it, not a completeness *audit* of the registry that was handed to it.

**Why this does not block the current verdict:** the four truncated `beta` `2x` cells are correctly
absent from the 290-row evidence base regardless of mechanism, and `beta` is not a candidate route.
But the vacuous-completeness-check gap is a genuine, generalisable process defect: nothing in the
current pipeline would have caught a *route subset that silently dropped a candidate-route cell*
the same way it dropped the beta cells — the only reason this one was caught is that a human
inspected the raw checkpoint files by hand (as the admission-set doc itself says: "the gap had to
be found by inspection rather than raised by the gate"). See recommendation below.

**Recommendation:** file this as its own issue (see reply to coordinator). The fix is to add an
explicit registry-completeness assertion *upstream* of route selection — e.g., a check that the
route subset passed to `mr-g5-reconcile*.R` equals the full frozen registry's cell set for that
cohort, or an explicit "N cells excluded, list them" log line — so that a future silent drop
(of a candidate route, not just an already-known-broken one) cannot pass calibration by omission.

### Q1 — Does `lognormal`'s tested parameter set reach parity with its own G3 claim, and is there an over-claim risk Fisher's inference lens would not see?

**Parity: yes, independently confirmed.** `docs/design/03-likelihoods.md:81` states the
`lognormal()` family has exactly two distributional parameters, `mu` and `sigma`, "defined on the
log-response scale," with "ordinary `mu` random intercepts." The `mr-lognormal` ledger row's
`dpar` field is `all fitted dpars` and its G3 `claim_boundary` promises "recovery of every fitted
distributional parameter for the ordinary random-intercept route." The G5 evidence set is
`fixef:mu:(Intercept)`, `fixef:mu:x`, `fixef:sigma:(Intercept)`, `fixef:sigma:z`,
`sd:mu:(1 | id)` — both dpars, each with an intercept and a slope/covariate term, plus the
ordinary random-intercept SD. That is exact parity with the G3 claim, not a superset or a
subset — the identical 5-parm, 15-cell shape I already verified for `gaussian` and `gamma` in my
original review (§1 of this file; both routes I approved carry the same five parm names).
I re-parsed the CSV directly rather than trusting the prior count: 15 rows, 1200/1200
interval-usable on every cell, coverage range 0.9317-0.96, 0 rows outside [0.925, 0.975] —
matching the coordinator's figures exactly.

**Two things Fisher's calibration lens would not surface, both checked and both clean:**
- **The centring defect that hit `gaussian` also hit `lognormal` in the prior (`2026-07-31`)
  cohort** — the lognormal calibration receipt on file
  (`docs/dev-log/evidence/2026-07-31-mr-g5-lognormal-calibration-receipt.md`) records the same
  symptom: `fixef:mu:(Intercept)` coverage pinned at 1.000 at all three rungs, and a
  `sd:mu:(1 | id)` `0.5x` cell short one usable interval (1199/1200). **Both symptoms are absent
  from the `authenticated_uncentred` cohort I re-checked**: `fixef:mu:(Intercept)` now reads
  0.9367 / 0.9442 / 0.9417, and `sd:mu:(1 | id)` `0.5x` reads 1200/1200 usable. This is a
  claims-lens check (is the promoted evidence actually the fixed cohort, not the stale receipt?),
  not a calibration check, and it passes.
- **Shared-code-path risk with the two known-defective T2 routes.** `lognormal` is built and fit
  by the *same* shared functions as `skew_normal` (frozen-DGP defect) and `student`
  (permuted-quantile defect) — `mr_g4g5_t2_dgp()` / `mr_g4g5_fit_t2()`
  (`inst/sim/R/sim_missing_response_g4g5.R:316-377`, route dispatch list at line 316 and 493).
  Sharing a builder with two broken routes is a real reason to look twice, and I could not find a
  written root-cause note in this worktree ruling `lognormal` out by name — a genuine gap, flagged
  as such. But the *symptom profile* of each known defect argues against it reaching `lognormal`:
  a frozen DGP produces degenerate coverage (pinned near 0 or 1, as centring did) or implausibly
  small MCSE from reused draws; a permuted quantile multiset produces systematic, off-nominal
  coverage. `lognormal`'s 15 cells show neither — 15 distinct, plausibly-varying coverage values
  (0.9317-0.96) with MCSE (0.0057-0.0073) matching the binomial-variance expectation at n=1200
  (√(0.95·0.05/1200) ≈ 0.0063). That is what a correctly-executed cell looks like, not what either
  known defect looks like. I am treating this as sufficient, not as a substitute for someone
  locating the actual root-cause note for the two "wrong-scale truth constant" cells and confirming
  by name they are not `lognormal` or `gamma` — that confirmation should still happen before this
  promotion is called final, but it is a documentation gap, not a contradiction I found in the data.

**Verdict: PROMOTE `lognormal` at all three rungs, same terms as the seven.**
